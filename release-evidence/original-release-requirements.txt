Setup Goal /Goal for below task: 
Build a production-ready local file-transfer application that makes transferring files between two laptops on the same Wi-Fi/LAN extremely fast, reliable, secure, and effortless.

The product should:

* Pair two laptops in seconds with minimal user interaction.
* Support single files, multiple files, folders, and very large files.
* Transfer directly over the local network at the highest practical Wi-Fi/LAN speed.
* Keep memory usage bounded even for 10 GB, 50 GB, 100 GB+ transfers.
* Resume interrupted transfers instead of restarting them.
* Recover cleanly from Wi-Fi drops, refreshes, sleep/wake, crashes, and reconnects.
* Verify transferred data using cryptographic hashes so corrupted files can never be reported as successfully transferred.
* Make pairing secure enough that files cannot accidentally be sent to the wrong device.
* Hide WebRTC, ports, networking, SDP, OPFS, and other technical concepts from normal users.
* Provide a simple UX: **Send → Select Files → Pair → Transfer → Verified Complete**.
* Show accurate transfer speed, progress, ETA, transferred size, and connection status.
* Require no internet or cloud storage for local transfers.
* Avoid forcing users to reselect or rehash huge files when only the connection fails.
* Handle thousands of files and multi-gigabyte transfers without freezes, crashes, corrupted state, or excessive disk/network overhead.
* Provide clear recovery actions whenever something goes wrong.

The release standard is:

**A non-technical user should be able to open the app on two laptops, connect them in seconds, transfer a huge file at near the maximum speed their Wi-Fi and disks allow, recover automatically from temporary failures, and receive a cryptographically verified copy without needing to understand how the application works.**

The application must prioritize, in order:

**Correctness → Data integrity → Reliability → Pairing simplicity → Transfer speed → Security → UX → Visual polish.**

# 2. CURRENT RECEIVER WRITE PATH MAY DESTROY THROUGHPUT

Inspect carefully:

`OfflineDestinationReceiver.acceptData()`

It currently reaches:

`store.writeBlock(index, payload)`

A WebRTC block is around 60 KiB.

`writeBlock()` delegates to `writeBlocks()` with ONE block.

The OPFS implementation then flushes payload data before persisting receipt state.

That means WebRTC may effectively perform a durability flush and journal operation for approximately every 60 KiB.

For a 10 GB file that is an enormous number of durable commits.

This is unacceptable if the product claims fast LAN/Wi-Fi transfer.

Redesign this path.

Use bounded batching while preserving crash safety.

Possible design:

* receive multiple validated blocks into a bounded batch;
* write batch payload;
* flush payload once;
* persist one receipt journal record containing all committed indexes;
* flush receipt metadata;
* ACK the entire durable block group together;
* sender treats blocks as complete only after batched durable ACK.

The existing `writeBlocks()` batching machinery should be reused where appropriate rather than reinvented.

Do not sacrifice durability to fake benchmark numbers.

Benchmark several batch sizes and select sensible adaptive defaults.

Consider:

* 16
* 32
* 64
* 128 blocks

or a byte/time-based policy such as:

* commit at 4–16 MiB;
* OR after ~50–100 ms;
* whichever occurs first.

Keep memory bounded.

Batch ACK messages too.

Do not send one JSON acknowledgement per block when hundreds can safely be acknowledged together.

# 4. REDESIGN RENDEZVOUS NETWORKING FOR RELIABILITY

Deep-review `scripts/rendezvous.mjs`.

Current signaling needs special scrutiny.

### UDP SDP payloads

The code permits SDP payloads approaching tens of kilobytes to travel through UDP.

Large UDP datagrams fragment at IP level and are unreliable on real Wi-Fi.

Do NOT rely on huge UDP packets for robust pairing.

Prefer:

**small UDP discovery + reliable TCP/HTTP signaling.**

Example:

Receiver runtime broadcasts a tiny discovery request.

Sender runtime responds with something tiny such as:

* protocol version
* room ID
* random challenge/token
* signaling port

Receiver's local Node runtime then uses a direct authenticated LAN TCP/HTTP connection to retrieve the SDP offer and submit the SDP answer.

File bytes must still use WebRTC directly.

If keeping UDP-only signaling, implement explicit small packet fragmentation/reassembly, checksums, retransmission and strict limits. But reliable TCP signaling is strongly preferred.

# 5. REMOVE AGGRESSIVE /24 NETWORK SCANNING

`unicastDiscoveryAddressesFromInterfaces()` currently appears to choose one preferred private interface and generate up to ~253 hosts from the first three octets.

Problems to investigate:

* assumes `/24`;
* ignores actual netmask;
* ignores other valid physical interfaces;
* misses peers on larger subnets;
* can generate hundreds of packets repeatedly;
* can look like network scanning;
* can trigger enterprise security tools;
* is unnecessary if subnet broadcast/multicast works.

Redesign discovery.

Preferred order:

1. loopback/same-runtime optimization;
2. subnet broadcast using actual interface/netmask;
3. a small LAN multicast discovery mechanism if appropriate;
4. additional physical interfaces;
5. graceful manual fallback.

Do not spray every possible `/24` host every 500 ms.

If a manual fallback is needed, make it extremely simple and hide it behind **Troubleshoot connection**.

Separate:

**pairing session state**.

Allow:

`Retry pairing`

Persist appropriate source directory handle + deterministic transfer identity using the existing large-sender resume infrastructure where possible.

On reload:

* request directory permission;
* verify that the source still matches;
* resume safely.

If the source changed, explicitly invalidate the prepared transfer.

Do not silently transfer changed content under an old identity.

# UX ACCEPTANCE TEST

Give the application to someone who knows nothing about its implementation.

They should be able to send a file between two laptops without reading the README.

If they need to understand ports, OPFS, Node, SDP, ICE or WebRTC, the UX has failed.

# IMPORTANT IMPLEMENTATION PRINCIPLES

Do not hide problems with giant try/catch blocks.

Do not convert corruption into success.

Do not disable verification for speed.

Do not solve crashes by loading everything into memory.

Do not delete partially received valid data unnecessarily.

Do not restart a 100 GB transfer because pairing failed.

Do not make the user repeat expensive hashing without a security/integrity reason.

Do not claim a device is verified unless it actually is.

Do not display “100% complete” before authoritative verification succeeds.

Do not call something “saved” until destination verification succeeds.

Do not introduce cloud dependencies.

Do not require internet access for transfer.

Do not add analytics, telemetry, trackers or external services.
