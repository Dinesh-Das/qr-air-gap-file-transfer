# Optional Windows x64 runtime bundle

Requirement L805 asks for a self-contained runtime if feasible without destabilizing the release. Keep the existing external-Node package supported. Add an explicit offline builder option, not a download or installer in the recipient flow.

The builder supplies a trusted directory containing official Windows x64 Node.js 24 `node.exe` and its complete matching `LICENSE`, plus the binary SHA-256 independently obtained from official versioned release checksums. The packager verifies the pin before executing the supplied binary for its version/platform/architecture, rejects other platforms, architectures and major versions, and copies the validated bytes and license. License markers catch incomplete input; they do not authenticate licensing provenance. Builders remain responsible for obtaining the complete matching official distribution. A local pin is not a signature or publisher authentication. Nothing in packaging downloads a runtime.

The optional package contains `runtime/node.exe`, `runtime/LICENSE`, and `runtime/ORIGIN.json`, all included in its existing copy-integrity manifest. START-HERE explains that Node installation is unnecessary for this variant, while a supported Chromium browser is still required. Windows ARM64 is outside this first variant. The launcher prefers its relative bundled executable, preserves exit codes, and uses PATH only if the bundled executable is absent. A present but broken executable must fail visibly instead of silently selecting another version.

Native command tests use a small launcher script fixture, real Node, cleared PATH or a controlled external runtime, unrelated working directory, and folder names containing spaces, `&`, parentheses and `!`. These prove command routing and exit behavior, not native browser opening. The packaged app also requires an isolated real-runtime lifecycle/served-byte check, manifest verification, blank physical template check and original external-runtime smoke. Full runtime compatibility gates and actual Windows browser/default-handler and two-laptop tests remain distinct. No READY claim follows from a packaging pass.

Preserve previous candidates. Do not ship the earlier feasibility prototype: its documentation still described the external-runtime package. The first implementation candidate must have matching generated instructions and licensing notices. The supplied runtime's copy checksum cannot verify itself before execution; trusted distribution and publisher verification remain prerequisites.

## Working-directory-independent external runtime

A native reproduction found that a harmless invalid `node.exe` in an unrelated working directory blocked a valid runtime on PATH (exit 216). The old `where.exe` check also allowed a working-directory `where.exe` to shadow its locator. The fallback now uses CMD's native `FOR` PATH-search modifier to select the full executable path directly. This avoids both working-directory searches and an external locator process. Bundled runtime preference, missing-runtime advice and child exit propagation remain unchanged.

The two native regressions failed with the old launcher while six existing cases passed. All eight cases pass with the correction, including Unicode, spaces and shell symbols in both bundle and runtime paths. The full Node 24.22.0 check passes 449 tests in 49 files, typecheck and build. Full Edge 88/Chrome 88 gates qualified the portable application's runtime and transfer files before this boot-only correction. New package validation must show that only the command launcher differs; the full browser runner starts the server directly and does not exercise this command file. Native CMD coverage and actual bootstrap checks are separate evidence.
